# rail-intel-nexus · 火车票产品情报中台

> 面向火车票产品团队的**内部情报 Agent**：把分散在政策/竞品/舆论三类渠道的信息，自动变成「可回溯的证据 → 带上限的结论 → 可执行的产品动作」。

这不是一个「看起来全绿」的演示页。它的核心是一条**可审计的流水线**：每一个数字都能追到某条原文、某次打分、某条影响规则；没有数据时它不会编数据。

---

## 1. 为什么做这个（业务场景）

火车票产品的关键判断，长期依赖「人肉盯」：

- **政策监管**：12306 / 国铁集团 / 交通运输部 / 国家铁路局 / 路局公告 / 12306 公众号。一条新规（学生票预约、儿童票判定、退改签费率、电子发票）会同时影响搜索、下单、支付、退改、客服多条链路。
- **竞品功能**：携程、去哪儿、飞猪、12306 App 的版本与入口变化（退票费预估、规则助手、候补解释）。
- **舆论反馈**：小红书攻略、微博话题、B 站科普、黑猫投诉、客服工单、用户调研——先于官方口径暴露「用户到底哪里没看懂」。

三类信息**节奏不同、可信度不同、口径还会互相冲突**。人工处理有三个典型失败：

1. **看到但没看懂**：拿到一条小红书「60 天预约」，不知道它和官方「30 天」冲突，直接传给业务。
2. **看懂但没排序**：一周 40 条线索，凭感觉挑 3 条，挑错了还会被追溯。
3. **排了序但没有下一个动作**：结论停在「建议关注」，落不到模块与负责人。

本项目的目标不是「自动下结论」，而是：

> **广泛采集 → 可解释打分 → 冲突隔离 → 参考意见（带证伪条件与使用边界）→ 人确认后记忆自进化。**

## 2. 它现在是什么（一句话架构）

```
18 个声明式信息源
   → 采集（RawDocument）
   → 归一化 + 双层去重（内容指纹 / 跨源近重复 / 跨运行复用）
   → 分类与实体识别（12 个产品模块）
   → 5 维打分 + 冲突二次打分（pass / warning / blocked）
   → 主题锚点聚合（8 个锚点）→ 事件
   → 19 条影响规则 + 3 条竞品 gap → 模块影响矩阵
   → 参考意见（act / watch / hold + 依据 + 证伪 + 验证动作 + 使用边界）
   → Markdown 报告（唯一真源）
   → 三层记忆写回（working / episodic / semantic）
```

10 个阶段逐段记账（`inputCount / outputCount / durationMs / metrics / notes`），在「流水线」页面可直接看到每一步掉了多少、为什么掉。

### 页面（10 个）

| 页面 | 回答的问题 |
| --- | --- |
| 总览 | 今天有没有值得动手的事？三类各多少？链路有没有断？ |
| 情报事件 | 这条事件的参考意见是什么？依据、证伪、验证动作、冲突在哪？ |
| 证据库 | 这条说法出自哪、几分、能不能作为政策依据？ |
| 信息源 | 18 个源哪些真的能采、哪些要登录、本期各产出多少？ |
| 采集任务 | 这一轮谁跑成功了、谁零新增（不是失败）？ |
| 产品影响 | 事件 × 12 模块的影响矩阵与机会点 |
| 报告 | 由数据生成的 Markdown 日报/周报/专题 |
| **流水线** | 每个阶段输入输出、耗时、指标、源覆盖 |
| **记忆中心** | 源先验怎么变、关键词权重、playbook、反馈日志 |
| **架构与边界** | MCP 契约、泛化矩阵、能力边界与下一步 |

## 3. 三个关键设计选择（也是这个项目最值得看的部分）

### 3.1 数据诚实优先：宁可用样本语料，也不用假数字

改造前：首页 6 个指标（26/14/5/2/3/1）、三大类卡片、一句话结论全是硬编码，日期冻结在 2025-07-10；「导出 PDF / 导出 Excel / 查看快照」都是 `toast` 假成功。

现在：

- 主链路用 `buildSampleCorpus(now)` 的 **24 条相对时间样本语料**，时间按「几小时前」生成 → 永远不过期、可复现；
- 所有样本数据在 UI、报告、MCP 返回值里都标注 `dataOrigin = sample`；
- 删掉了 mock-data 文件与所有假导出按钮；
- 页面上的每个数字都由 `runPipeline` 现算。

> 这条选择背后的判断：**内部情报工具的信任成本极高。一次「假成功」被用户发现，后面所有结论都会被怀疑。**

### 3.2 打分可解释 + 冲突隔离：让「不能采信」这件事有地方放

5 维加权（总分 100）：

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 来源权威度 | 25 | S/A/B/C/D 映射，官方源额外加成 |
| 可核验性 | 20 | 有原文 URL、有明确生效日期/数字、有快照 |
| 多源印证 | 20 | 同一主题锚点下的独立来源数 |
| 时效性 | 15 | 24h 内 1.0，7 天衰减到 0.2 |
| 信息密度 | 10 | 数字、日期、条款密度 |

叠加：历史先例最多 +8；**检测到与高权威源口径冲突 −20**。

冲突判定（规则版，不用 LLM）：权威级差 ≥ 2 且（命中「未证实/不一致/与官方/辟谣/未在/存疑」等标记，或「天数」口径不一致）→ 双方标记 `conflict`，事件进入 `human_review`，`stance` 自动降为 `watch`。**任何冲突证据都不得 `canBePolicyEvidence`。**

### 3.3 自进化但人在环：反馈只改「权重」，不改「事实」

三层记忆：

- **working**：本轮运行 ID、已见内容指纹、未结主题、临时笔记；
- **episodic**：事件卡（≤40 张，含人工决策 confirm/reject），提供「历史先例」加成；
- **semantic**：源先验 `Beta(6·base, 6·(1−base))`、关键词权重、playbook 规则、阈值。

一次人工反馈（确认/驳回/提升/降级）会触发：

1. 源先验后验更新（`Beta` 平滑，避免一次误判把源打成 0）；
2. 事件主题词权重 ±0.12（clamp 0.1~1）；
3. **同一事件第 2 次被确认 → 自动生成一条 learned playbook 规则**；
4. 写入 `FeedbackRecord`（含 `scoreBefore`，可审计）；
5. 立刻重跑流水线，让效果在下一屏可见。

没人确认时，系统不会自己「学会」什么——这是与「全自动 Agent」的刻意区别。

## 4. 怎么跑

```bash
npm install            # 或 bun install（仓库以 bun.lock 为准）
npm run typecheck      # tsc --noEmit
npm run build          # vite build（会重新生成 routeTree）
npm run verify         # 引擎自检：阶段计数 / 事件 / 报告 / 反馈闭环 / 二次运行
npm run dev
```

`npm run verify` 会打印类似：

```
plan 18→17  ingest 18→23  normalize 23→23  dedupe 23→22  classify 22→22
score 22→20 cluster 20→5  judge 5→5  report 5→1  memory 5→5
docs=23 newEvidence=22 dup=1 blocked=2 events=5
源覆盖：17/18 个源本轮有产出

FEEDBACK 闭环：源先验 src-10 0.780 → 0.811，episodic decision=confirm
RUN 2（带记忆）：newEvidence=0 events=5（复用旧证据，不重复入库）
```

> Windows 说明：`@lovable.dev/mcp-js` 的 vite 插件在 Windows 上存在路径分隔符比较 bug，`vite.config.ts` 在 win32 下默认跳过该插件（部署环境 Linux 不受影响），需要本地验证 MCP 时设 `MCP_PLUGIN_FORCE=1`。

## 5. MCP：给内部 Agent 的只读契约

`/mcp` 暴露 6 个工具（v0.2.0，全部返回引擎现算结果）：

| 工具 | 用途 |
| --- | --- |
| `get_overview` | 运行信息、源覆盖、风险分布、最高优先级事件的一句话结论 |
| `get_daily_brief` | 直接取 Markdown 日报（可贴飞书文档/群消息） |
| `list_sources` | 源注册表 + 本轮真实产出（原文数/新增证据/去重数） |
| `list_evidence` | 证据 + 评分拆解 + 校验状态 + 是否可作政策依据（支持分类/来源/最低分过滤） |
| `list_events` | 事件列表（按等级/状态/类型/立场过滤） |
| `get_event` | 事件详情：参考意见、时间线、冲突、影响矩阵、证据原文 |

**预留的内部结合点**：内部策略库 / PRD 库可以作为额外 MCP 工具接入（`get_policy_context`、`search_prd`），把「情报 → 内部规则」的比对从人工变成工具调用；当前版本不接，是为了不假设内部数据结构。

## 6. 边界与已知问题（不藏）

- **未接真实抓取**：`/api/collect`（白名单 + 失败降级）尚未实现，18 个源里 12 个标记 `login_required`/`auth_required`；本期数据是**样本语料**，不是真实抓取。
- **未用数据库**：Supabase 客户端存在但业务 0 引用；仓库只有 RLS 迁移、没有基础建表迁移；只有 publishable key。数据落 `localStorage`（`ttih:v2`），刷新不丢、换设备不同步。
- **MCP 未鉴权**：`.lovable/mcp/manifest.json` 仍是 `auth: none`，只适合内网/演示；上线前必须加 OAuth 或网关鉴权。
- **影响规则是规则表**，不是模型：命中靠关键词，会有漏判；19 条规则是冷启动基线，靠 feedback 逐步替换。
- **报告只出 Markdown**：PDF/Excel 导出已移除（此前的实现是假 toast），需要真实导出时再接。

## 7. 下一步（按投入产出排序）

1. **Phase 1｜打通 3 个真源**：12306 公告（RSS/HTML）、12306 公众号、App Store 评论；`/api/collect` 走域名白名单 + 超时降级 + 失败任务留痕。
2. **Phase 2｜证据校验升级**：URL 可达性检查 + 快照存档（对象存储）+ 生效日期抽取，`verified_online` / `verified_snapshot` 变成真状态而不是规则推断。
3. **Phase 3｜内部结合**：接内部策略库/PRD 的 MCP 工具，产出「现有实现 vs 新规则」的差异清单，参考意见里直接引用 PRD 条款。
4. **Phase 4｜交付形态**：飞书机器人推送 P1（卡片 + 报告链接）、MCP 加鉴权、周报自动归档。
5. **Phase 5｜工程基线**：单元测试（打分/去重/聚合/记忆纯函数）、CI（typecheck + build + verify）、迁移基线（12 张表建表 SQL）。
